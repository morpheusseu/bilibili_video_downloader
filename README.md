# Bilibili 视频 / 音频下载器

基于 **bpi-py 0.3.1** 的独立 PyQt5 桌面应用；也提供共享同一下载引擎的 CLI。不依赖 Boxy。

## 功能

| 输入 | 能力 |
| --- | --- |
| BV / AV ID、视频链接 | 指定分 P、链接 `?p=2`，或下载全部分 P |
| 收藏夹 ID、包含 `fid=` 的链接 | 按服务器 `has_more` 分页，去重后批量下载 |
| UID + 收藏夹名称正则 | 匹配一个或多个收藏夹；空正则匹配全部；跨收藏夹去重 |
| `ep123`、番剧单集链接 | 使用 bpi-py 的番剧元数据和播放接口，不抓网页字符串 |
| 输出 | MP4 音视频合并；MP3 / WAV 音频提取与转换；支持 DASH 和分段合并 |
| 登录 | 真实 Chrome 中的官方登录页面；手动扫码、密码或平台要求的验证 |
| 私信 | Broadcast 实时通知、按会话增量收信、昵称/头像及未读数量；按需历史与确认后文字回复，不标记已读 |
| 账号浏览（只读） | 统一关注动态流和观看历史；独立关注名单、特别关注、所选 UP 主的动态/视频投稿与本页个人互动比例 |

界面支持不下载媒体的内容列表预览、输出目录选择、实时字节进度、取消、打开输出目录。
下载/转换在独立线程的 asyncio 循环里运行，不阻塞界面。主要操作按钮固定显示。
公开内容无需登录。仅下载当前权限允许的内容；不绕过 VIP、地区限制、DRM 或风控。

## 界面与使用流程

1. 在“内容来源”粘贴链接或 ID，选择单个或全部分 P；可先“检查来源”查看前 10 个分 P。
2. 在“保存设置”选择 MP4 / MP3 / WAV 和目录。音频格式不需要选择画质，已有文件不会覆盖。
3. 点击“开始下载”会展开底部详情；可随时点击圆形下箭头收起，开始和取消按钮始终保留。
   空闲时及任务成功完成后详情自动收起，再次点击可查看日志并打开文件夹。
4. 需要账号权限时，点击右上角圆框内的粉色“登录”，打开账号浮窗。
   登录后，同一圆框显示头像，旁边显示用户名；点击头像仍可管理登录。
   Cookie、FFmpeg 路径和操作详情按需展开。
5. 登录后，点击右上角黄色星形图标进入“我的收藏”，列出自己创建的收藏夹。
   选择收藏夹可浏览内容、UP 主、时长和失效状态，每页 20 项，按需“加载更多”。
   双击可用视频或点击“填入所选视频”，再在保存设置中确认下载；也可填入整个收藏夹。
6. 星标旁的信件图标打开“私信”。Chrome 登录/恢复成功后自动建立实时订阅，收到通知才定向读取对应会话。
   列表、正在查看的消息及未读数自动更新，草稿和选择保持；会话列表和每条消息均显示头像。
   可刷新消息或加载更早消息，输入文字后点击“发送”并确认收件人。Enter 换行，⌘/Ctrl+Enter 进入发送确认。
   私信与收藏面板互斥展开；折叠私信面板仍接收通知，但不会扫描所有会话历史。
   点击私信标题旁的 ↗ 可扩大为独立 IM 窗口：左侧会话、右侧消息与回复，聊天区随窗口伸展。
   浮窗复用原面板、草稿、缓存和 Broadcast 连接；↙ 或关闭浮窗返回主窗口，不重新连接或读取正文。
   每条消息的头像对齐第一行，多行文字和高图片不会让头像移到中间。
7. 右上角“浏览”进入“关注动态 / 观看历史”两个只读标签。首次打开当前标签才读取，
   可“加载更多”、选择条目查看纯文本详情，或点“打开原文”在浏览器访问固定的 Bilibili 页面。
   重新打开已经加载的标签复用缓存；“刷新”重新读取第一页，不启动下载或其他写操作。
8. 右上角双人“关注”图标进入独立名单；特别关注在头像上显示金边并置顶，不再占用额外类型列。
   名单每页最多 50 人，可只看当前已加载名单里的特别关注，不把首屏当作全部关注者。
   点击“采集全部最新页”，先分轮收齐名单及每位关注者最新一页动态、最新一页投稿，
   内容页收齐即完成，不再枚举所有视频核验个人互动；可随时暂停，重启后点“继续分轮采集”继续。
   选中 UP 主即可查看保存页面，或显式查看下一页、检查最新页；全部采集不自动回溯历史。

下载进度和日志明确标为“视频流（画面）”“音频流（声音）”；它们属于同一个视频，
完成后合并成一个 MP4，并非下载了两个视频。普通分段流标为“同一视频的音视频片段”，
DASH 音频输出只读取音频流；普通音视频分段则在下载后提取音频。任务结果显示最终成品文件数。

圆形下载入口的红点统计**本次运行中，自上次展开详情后新生成的成品文件数**，
不把音视频流分别计数，也不统计已存在而跳过的文件；展开详情清零，超过 99 个显示 `99+`。
下载中收起时，外圈细环表示**当前文件的估算百分比**，不是整批收藏夹的总进度：
各媒体流等分前 95%，字节进度推进当前流，最后 5% 留给转换与原子发布。
这样画面和声音切换时不会从 100% 倒退；批量中的下一个文件单独从头计进度。
尚未取得长度时用虚线弧表示处理中，只有成品实际发布后才到 100%，不增加额外探测请求。
失败或取消会展开详情，已完成文件保留；不会用折叠入口隐藏错误。

整体界面以蓝色为主要操作色，登录和收藏分别使用粉色、黄色语义图标；配合系统字体、浅色卡片与清楚的文字层级，依据用户指定的
[Apple 设计参考](design/README.md)适配原生桌面工具，不引入远程字体、WebView 或装饰性动画。
支持最小 760×650 窗口；表单可以滚动，主要操作保持固定。改变来源后旧预览会清除，
不会在打字、切换设置或展开面板时自动访问 Bilibili。
例外是登录后的私信订阅，以及明确打开的账号面板：收藏夹和账号浏览首次读取当前列表，
之后仅按下面的前台检查或用户操作规则请求；不会在登录时自动扫描动态、关注和历史。

## 关注动态、关注的人与观看历史（只读）

- 三个标签共用原有后台线程、bpi-py 客户端、账号缓存和请求闸门，不另建账号或绕过节奏的通路。
  所有 API、封面和头像请求仍串行、间隔 0.5–1.5 秒；遇到风控停止本实例，不自动重试。
- 动态使用统一关注流，不逐个扫描 UP 主。正文、类型、作者、发布时间、视频信息或图片数量按平台实际结构显示。
  转发同时展示接口附带的第一层原文作者、正文、标题和图片数量；不递归展开、不读取原文图片，
  缺失或不可见时明确提示，可通过“打开原文”查看。视频使用原比例封面，其他动态使用圆框作者头像，
  不为图文或转发另取原图；图片加载、列表刷新和重绘均保持同一角色。
  此列表不等于关注者的全部操作，不包含其私密浏览记录或所有点赞、评论。
- 默认每 60 秒仅在“关注动态”标签可见、应用前台、非最小化且没有前台任务时调用
  `dynamic.check_new(update_baseline=...)`。没有新增就复用正文；有新增才读最新一页，
  更早内容可重新分页。“刷新”直接重新读取首屏，用于核验旧内容编辑等新增检查看不到的变化。
  这不是已验证的 Broadcast 推送，也不是完整的变更日志；不能保证发现所有编辑、删除或互动变更。
- 关注列表使用当前账号的 UID 每页最多 50 人读取，展示昵称、头像、UID、签名等平台字段；
  首次打开、手动刷新、翻页或分轮采集时请求。计数与列表可能在采集期间变化，不据此自动推断取关或联系人权限。
  名单和分页边界完整持久保存，不再受 200 人上限影响；旧的每页 20 人游标在同一轮沿用原页大小，
  手动从头刷新或重新采集时统一使用 50 人，避免中途更改页大小而漏项。
  独立“关注”页使用接口的 `special=1` 或 `tag` 包含 `-10` 标注特别关注，不从昵称或互动频率猜测。
  特别关注仅在本地稳定排序置顶，头像金边在占位图和真实头像更新后保持；不改变 provider 分页顺序。
  早期缓存没有保存该字段时显示“未核验”，打开名单后校验当前页，不删除其他缓存。
- 观看历史使用 `historytoview.history_list()` 的复合游标 `max/view_at/business` 按需分页，
  展示标题、作者、观看时间和播放进度。它是 B 站保存的观看记录，不是 Chrome 历史，
  也不承诺保留每次重复观看；不上传进度、不修改历史开关、不清空或删除记录。
- 动态 ID、UID 和历史实体/观看时间用于本地去重。分页不推进、异常或取消均保留先前列表与游标；
  错误会取消动态自动检查，用户确认后可手动刷新，不把失败或残缺页面当作“全部已采集”。
- 图片沿用共享可见范围缓存、安全 CDN 域名、无 Cookie、限长和随机间隔，不自动下载原图或播放媒体。
  统一动态流和观看历史各最多持久缓存 200 条已加载内容和相匹配的分页游标；关注名单完整保存。
  重启后标明“本地缓存”；继续向前只读下一页。动态流和观看历史显式加载超过 200 条时仍可在本次内存浏览，
  但不会把更远游标存到缺失页面之后；重启从最后完整缓存页恢复。
  不在登录时全量扫描，正文只写账号缓存、不写设置或操作日志；换号清空界面，“退出并忘记”删除该账号持久缓存。

## 关注者的最新内容与个人互动（只读）

- 在关注名单中选择某个 UP 主后按需读取，或点击“采集全部最新页”分轮收集；动态使用同一 SDK 的 `feed/all?host_mid=...`，
  视频投稿沿用 SDK 的 WBI 签名及传输读取 `/x/space/wbi/arc/search`，保留其忽略的合作标记。
  上一页、下一页显式操作，检查最新页不会遍历历史。
  合作投稿保留接口返回的实际作者，并明确标注合作；仅在 `is_union_video=1` 时接受空间主人与上传者不同，
  普通稿件作者不符仍报错，不把整轮采集卡在合法的合作稿件上。
- 所选 UP 与全量采集共用一个可抢占的异步读取通道；读取不再禁用整个界面。
  快速切换用 150ms 合并，只请求最终选择；新选择取消旧读取，让当前 UP 优先，随后全量采集从检查点继续。
  迟到结果按登录身份、选择票据及页面目标丢弃；SQLite 仍只在原后台线程读写。
  正文和已知状态先显示，点赞、投币后台补齐，缓存命中也会核验缺失/过期的观测；
  阅读、滚动、切换 UP 和标签不必等全部互动请求结束。“停止读取”保留已完成结果。
  HTTP 仍共用串行的 0.5–1.5 秒节奏；界面异步不通过提高请求密度来实现。
- 全部采集以一次完整关注名单为工作范围，不按当前“特别关注”筛选截断。
  先分页收齐名单，再交替读取每人的动态首屏和投稿首屏，正文页收齐即完成。
  不再进入全局视频互动扫描；列表内已经提供的动态状态、标题、作者、封面等直接使用，
  不额外逐条取详情。统一关注流的一页不能证明某位 UP 的首屏完整，因此不拿它冒充完整的个人动态页。
- 每轮最多处理 6 项，轮间让出界面和请求队列，继续共用 0.5–1.5 秒的 HTTP 间隔。
  后续轮次仅在关注面板可见、应用前台、非最小化且没有其他操作时启动；不会后台扫描全部关注者。
  “暂停采集”或底部取消立即结束当前任务；已取得的页面、个人观测及成功项检查点保存。
  失败不自动重试，缺页时回退修复相应进度；换号隔离，“退出并忘记”一起删除该账号的工作计划。
  完成只表示计划内每位关注者都已取得其请求时的最新内容页，
  不表示全部个人互动已核验或同一时刻的服务端事务快照。
- 账号、UP 主、动态/投稿分别隔离。正文页与下一页游标原子保存，已读旧页优先本地展示，
  重启后可复用；缺页或损坏时不会越过缺口。最新页检查间隔至少 60 秒，只有打开或手动检查时执行，
  不为每个 UP 主创建后台轮询。首屏成员、顺序或游标变化会重置依赖它的旧分页，避免混用位置而漏项。
- 页面和个人互动事实分别缓存；统计从这些持久事实在本地计算，没有另一份独立计数。
  一个视频的个人点赞/投币只用一个 `GET /x/web-interface/archive/relation` 查询，动态卡片与投稿列表共享结果，
  **仅在当前查看页**补齐缺失、过期或存疑的观测，不补扫其他 UP 或已读旧页。
  “校验本页互动”立即核验当前页；动态页同时重读当前内容页，核验动态本身的状态。
- 账号级近期索引读取 `/x/space/like/video`、`/x/space/coin/video` 和本人空间动态首屏，
  用正向记录发现近期点赞、投币和转发，不要求先知道所有视频/动态 ID。
  三个来源独立保存检查时间；10 分钟内复用，选中 UP 时先展示内容再检查到期来源。
  关注页在前台、非最小化且空闲时每 60 秒调度一次，到期才发请求；没有到期来源时不重新获取正文。
  全部采集或其他操作期间不插入这项检查。“检查近期操作”可立即重读三个来源并校正当前页。
  这些有限列表不是完整历史或动作日志：新出现的记录能确认正向状态，消失仅让旧状态待核验，
  不能当作取消点赞、取消投币或删除转发。失败来源保留旧值并停止自动重试，须显式检查才再尝试。
  观测及来源检查点在同一账号缓存事务保存；换号不复用，退出并忘记一并清理。
- 统计仅代表**当前页**：比例是“有该行为的条目数 ÷ 当前已核验条目数”，
  同时显示“已核验 n/本页总数”和待核验数量；未知、过期或存疑的记录均不参与分母。
  不是对这位 UP 主全部投稿的占比；投币按是否投过币计数，不累加币数。
  每条内容分列显示点赞、投币和转发；过期或存疑时保留上次状态并标“待核验”，
  提示及正文显示上次确认时间；全部未知或过期时不显示 0%。
- 动态点赞取动态自己的 `module_stat.like.status`，视频投稿点赞取该视频的个人状态，
  两者不相互替代；动态页的投币指其附带视频，非视频动态没有明确状态时显示未知。
  转发接受明确的个人 `status` 或本人动态首屏中指向原动态的转发记录，选用较新观测。
  全站转发总数不能说明本人是否转发过；没有可靠的取消推送或完整历史，因此仍可能未知或待核验，
  不为此扫描所有转发者，也不声称能即时发现其他设备上的取消操作。
- 首次打开含 20 个未缓存视频的一页，最多增加 20 次互动读取，按 0.5–1.5 秒逐条执行，
  先展示正文，再显示核验进度；可通过底部“取消任务”结束，已经取得的页面和观测保留。
  所有请求与下载、私信共用同一账号和请求闸门，遇到拒绝/风控停止，不自动重试；
  投稿接口即使返回 HTTP 200、但带 `is_risk=true`，也停止共享闸门。
  这里只读，不点赞、不转发、不投币，不上传观看记录；图像依旧按可见范围复用现有缓存。

## 收藏夹刷新与缓存

- 登录验证本身返回用户名和头像 URL，不额外请求用户资料。头像图片每次登录只读取一次，
  仅接受受信 Bilibili 图片 CDN、HTTPS、限长图片响应，不带登录 Cookie、不跟随跳转；
  图片失败时显示用户名首字，不让有效登录失败；同 URL 优先复用账号本机图片缓存。
- Bilibili 当前接口没有可直接读取的收藏夹 SHA。应用调用 bpi-py 的 `resource_ids`，
  对排序后的 `(type, id)` 集合计算本地 SHA-256，作为**成员变化提示**，不是服务端认证快照。
  每次仍需传输 ID 列表（大小随条目数增长），但不会为未变化的内容重复请求详细条目。
- 默认每 **60 秒**检查当前夹的资源标识；收藏夹列表独立缓存 **10 分钟**，首次进入或到期后才重新读取，
  空列表也按同样间隔检查。“强制刷新”立即重读列表、当前夹标识与首屏内容，不等待到期。
  以上自动检查仅限“我的收藏”展开、应用前台且没有其他任务时，不逐个扫描所有收藏夹。关闭窗口、最小化、
  切到其他应用或进行下载/登录时不会轮询。可随时取消勾选自动检查。
- 已加载条目按账号、收藏夹和页持久保存，目录、所选夹、已加载页数与分页边界同步提交。
  进入已浏览的收藏夹或重启恢复时先立即显示“本地缓存”，再在原后台线程检查变化，
  不用等 ID 请求和随机间隔结束后才显示。切换收藏夹不丢弃其他夹已经加载的页，
  “加载更多”从保存的下一页继续；不在登录或换夹时自动扫描所有正文。
  收藏条目不会按消息缓存的 30 天期限淘汰，保留至该夹分页失效重建或“退出并忘记”。
- 标识未变化时复用已加载条目、选中项与本次窗口的滚动位置；成员变化后回到第一页，
  同时丢弃该夹失效的旧分页。定期元数据检查若确认首屏顺序及文件夹修改时间一致，
  保留已经加载的后续页；缺页或缓存损坏时重新读取首屏，不跨过缺口恢复游标。
  分页位置指已加载页和下一页，不是跨重启保存的像素滚动位置。
- ID 摘要无法发现标题、简介等变化。因此当前夹的元数据最长 **10 分钟**重新读取一次第一页，
  “强制刷新”可立即更新；这不是用户操作的退避时间。所有实际请求仍共用 0.5～1.5 秒间隔。
  无变更且持续前台一小时约为 6 次列表、60 次标识及 6 次首屏元数据请求（不含首次加载、图片与私信），
  不随收藏夹数量倍增；当前夹的 ID 响应体仍随条目数增长，不是只下载一个服务器 SHA。
- 仅当已返回的条目缺少标题或封面时，使用 `fav.resource_infos(resources=...)` 每批最多 20 个补齐，
  完整条目不增加查询。批量结果按账号缓存 10 分钟，同一资源跨收藏夹及重启复用；
  只补公开显示字段，不改变文件夹成员、排序、收藏时间或个人操作状态。
  不匹配或重复的返回标识报错；已删除/私有资源未返回时保留占位，不转为逐视频重试。
- 分页以实际 `has_more` 为准，不信任可能延迟的数量统计；遇到空转分页报错。
  标识与条目不一致时不把缓存标成“未变化”。加载下一页前也检查成员变化，避免混入旧分页。
- 刷新失败或被取消时保留原缓存并暂停自动检查，没有自动重试；触发风控则沿用全局停止策略。
  退出或换号清空界面，“退出并忘记”删除该账号持久缓存，不影响其他账号。此功能不修改任何收藏。
- 条目封面按屏幕可见范围逐张读取，滚动做 180ms 合并；折叠、非前台或有任务时不发起新请求。
  图片使用现有的 HTTPS `hdslb.com` 白名单、无 Cookie、禁止重定向、20 MiB 限长与共享请求间隔。
  图片在同一后台线程读取，不阻塞界面；下载、登录或私信读取会取消可选图片任务并优先执行。
  封面与私信头像共用按解码后像素字节量控制的 256 MiB 内存缓存，不限制张数；
  相同 URL 复用，不随收藏标识检查重复下载，超出字节预算时淘汰较旧的记录；
  另由账号磁盘缓存供重启复用，见下面的缓存边界。
  加载失败显示占位图；网络/风控错误暂停后续封面，“强制刷新”才允许再尝试，不清除有效条目。

## 私信浏览与文字回复

- Chrome 登录/恢复后建立一条 [官方网页 Broadcast](https://s1.hdslb.com/bfs/seed/crayon/im/message-notify.js)
  WSS 连接：`proto` 子协议、鉴权及 `Notify/WatchNotify` 订阅，不是 MQTT，也不是私信定时轮询。
  通知只是唤醒提示；正文仍只由 bpi-py 读取，不把通知当作另一份消息数据库。
- 相邻通知做 350ms trailing 合并，最长等待 1.5 秒；一条消息的“取正文/更新会话/更新未读”
  通知合成一批。已知单聊先按上次成功的 `begin_seqno` 定向拉取，再检查两个会话类别的首屏；
  新联系人先读列表以验证目标。后台合并首屏时保留已加载的旧页面，不遍历其他会话正文。
- 首次读取某个会话只取最新 20 条建立基线，不假称已加载全部历史。后续超过 20 条的新消息
  用固定下界和递减上界排空增量，成功后才推进游标；单批超过 500 条、身份不符、分页不推进均暂停而不跳过。
  正在查看的会话合并去重，保留已读到的旧页；查看仍不发送已读确认，也不清空草稿。
- “仅最近 20 条有我发言”只筛选当前列表里已取得最近页的普通私信。
  最新一条若由本人发送也能直接判定；其他未读取或尚待补增量的会话标为“未判断”，
  开启时暂不显示，取消筛选后可按需打开。它不代表完整聊天历史，也不把旧页里的一次发言当作最近参与；
  系统提示、撤回及视频自动推送不算本人发言。切换筛选只改本地显示，不请求正文、不标记已读，
  不改变 Broadcast 收信对象；过滤掉的会话仍可正常接收并缓存新消息。
- 心跳每 20 秒按最近入站消息重新计时，连续四个周期没有任何响应视为网络断线，进入有界恢复。
  心跳/传输确认不占用长时间媒体下载的 HTTP 锁；所有正文、列表、头像等 HTTP 请求仍共享 0.5–1.5 秒间隔。
  下载占用该队列时正文可能延迟，但通知与心跳继续处理，不丢弃待处理会话。
- 每次切回应用前台，在现有连接上发一次协议心跳检查，10 秒未收到匹配响应才判失效；
  相邻检查合并，不重复建连接、不重扫历史。一个本地 5 秒定时器检测超过 15 秒的调度暂停，
  用来覆盖系统休眠后仍保持前台的场景；正常定时器 tick 不发网络请求，不修改系统休眠设置。
- 普通传输断线、网络/心跳超时自动重连。每轮最多重试 5 次，随机指数退避依次为
  1–2、2–4、4–8、8–16、15–30 秒；成功完成鉴权和订阅才算连接成功，稳定且心跳正常满 2 分钟才重置失败计数。
  达到上限后暂停，等新的前台/唤醒检查或手动点“恢复实时连接”；新一轮距离最近一次连接尝试开始至少 30 秒，
  不能靠连续切换窗口绕过进行中的退避。只有 Broadcast 客户端拥有这一连接与重试状态机。
- 鉴权/HTTP 拒绝、服务端踢出、协议/身份错误和风控不自动重试，也不会因切回前台自动恢复。
  风控沿用实例级停止策略，不能用恢复按钮绕过。关闭窗口、退出或换号取消连接、退避与待处理读任务，
  旧账号结果不能回填到新账号界面。自动和手动恢复均检查已读取会话的 frontier，定向补断线增量，保留草稿和选择。
- “私信”标题右侧的小点：黄色为连接/鉴权订阅中，绿色为已连接，红色为断开、等待重试或已停止。
  鼠标提示和下方文字说明具体状态、等待时间和错误原因，不只靠颜色区分。
- 已收到的会话、消息、昵称和头像 URL 存入账号本机缓存；未选中的会话收到通知时也保存正文，
  不只保存序号。每个会话的正文和 forward 游标是一个原子记录，写入失败不推进内存或磁盘游标。
  重启先展示标明来源的缓存，再由 Broadcast 连接后的会话首屏检查补增量；刷新/发送前检查也先排空缺口，
  不会直接把 latest 页最大序号当作已完整收到。更早历史仍需显式分页，不承诺完整离线归档。
  诊断日志保留连接、心跳、前台/唤醒探测、重连退避、通知及定向读取的数量和停止原因，
  不记录 Cookie、通知原始包或私信正文。
  macOS 日志位于 `~/Library/Application Support/Bilibili Downloader/logs/broadcast.log`，单文件 1 MiB、最多两份轮换。
  同一日志还记录 API/图片请求的进程号、共享队列序号、固定白名单接口名、方法、状态码、数值 API code、
  耗时、距上一请求完成的间隔及响应字节数。未知 API 路径只记作 `other_api`，所有图片统一记作 `cdn.image`。
  不记录 URL、查询参数、headers、Cookie、请求/响应正文、用户/收藏夹 ID 或异常原文；`status=0` 表示未取得响应。
  收藏日志区分列表/正文的 `fetched` 与 `reused`，图片磁盘命中只记录字节数，不发 HTTP 请求。
  自动刷新受前台、空闲和 60 秒调度约束：列表满 10 分钟后在下一次检查读取，并非精确的独立 10 分钟定时器。
- 按 SDK 的[私信接口说明](https://github.com/Yuelioi/bpi-py/blob/main/docs/private-message-api.md)，
  `ALL=4` 在真实服务上可能忽略历史游标；因此分别读取普通/系统与未关注两类，每类每页 20 个，
  合并去重并验证时间游标前进。未读取的下一页明确显示“更多会话”，不假称首屏完整。
- 昵称和头像地址按当前页 UID 批量读取，不逐个调用用户资料；失败时保留有效会话并显示 UID。
  列表和消息头像按可见范围读取、共用安全图片通路与缓存，发送时让位；当前账号头像直接复用登录结果。
  普通用户单聊可展开，群/系统会话不冒充单聊读取。
- 消息每页 20 条，按序列号去重、升序展示；更早消息使用最早序列号作为上界。
  时间戳按秒解释为本地时间；不把未知时间假标为 UTC。支持通知卡片、系统提示、图片、自定义表情以及视频/直播分享摘要。
  类型 11 是[视频推送卡片](https://github.com/pskdje/bilibili-API-collect/blob/main/docs/message/private_msg_content.md)，
  展示接口已有的标题、简介、时长、视频引用、UP 主赠言和封面；字段缺失时保留安全摘要，不额外查询视频详情。
  文字中的表情名称按同一次正文响应返回的 `e_infos` 的 `text/url` 映射为图片，
  映射随消息原子保存，重启后仍可复用；可选表情元数据不完整时保留文字，不阻断有效正文和游标。
  `provider_views.py` 扩展 pinned bpi-py 0.3.1 忽略的 `e_infos`、动态 `orig` 和投稿 `is_union_video` 字段，
  沿用 SDK 的认证、签名、传输和错误处理，
  不为每条消息或转发额外查询详情。旧消息未保存的表情映射可通过“刷新消息”补充；
  缺少当前展示字段的旧动态快照不会被当作有效内容复用，首次打开时按页重建，不清空消息或图片缓存。
- 私信图片和表情只在消息可见时按需读取，复用头像/封面的账号缓存、受信 CDN、无 Cookie 和 0.5～1.5 秒间隔；
  每张响应最多 20 MiB、解码尺寸受限，GIF 只显示静态首帧，不自动播放或下载音视频附件。
  消息原文统一转义，界面只插入已加载到内存的图片，不执行 provider HTML、外链或跳转按钮；复制仍保留原文与表情名称。
  正文和选中态明确使用应用配色，不继承系统深色模式的白字到浅色消息背景。
  未识别或损坏类型保留明确占位，已撤回消息不显示原文、表情或图片。
- 私信域名只放行列表、消息读取和批量昵称三个 GET 路径，以及文字发送的固定 POST 端点；
  不开放已读回执、删除或其他写操作。回复只面向已读取列表中的普通用户单聊，群/系统会话不发送。
  未读数量保持服务器返回值，不因为本应用查看就清零。日志只记操作结果和数量，不记私信正文。
- 取消、失败或分页未推进时保留此前成功结果；认证失效、429/风控及模型不匹配明确提示，不自动重试。
- 文字回复按收件人 UID 保留本次运行内的草稿；确认框明确显示昵称、UID 和原文，确认后再次核对账号与草稿。
  只有 Cookie 的账号字段与验证身份一致、含发送所需 CSRF 时才能提交。编码后正文上限 2000 字节，保留换行。
- 每次发送先读取最新消息边界，只提交一次，再回读。非零消息编号用于精确核对；网络结果未知时，
  只有边界后唯一一条、由本人发出且原文相同的新消息才视为对应回读结果，不靠历史同文消息猜成功。
  发送时禁止取消，防止误以为取消就能重发；只有回读确认后才清空对应草稿。
- 发送超时、响应缺少编号或回读失败时保留草稿并锁定重发；“核对发送结果”只读取，不再次 POST。
  未发现对应消息时保持待核对，可到官方客户端检查。当前没有服务端幂等保证，不能承诺跨设备严格 exactly-once。
  待核对信息仅在本次运行内存中保留；退出/忘记前提示风险，重启不自动重放任何发送。

## 安装和运行

需要 Python 3.11+、[uv](https://docs.astral.sh/uv/)。账号登录额外需要已安装的 **Google Chrome**。

```sh
uv sync --frozen
uv run --frozen bili-downloader
# 等价的源码入口：
uv run --frozen python main_window.py
```

FFmpeg 优先使用用户指定路径，其次系统 PATH，否则使用 `imageio-ffmpeg` wheel 自带的二进制。
无需为了首次运行单独配置 FFmpeg。可在界面的高级设置里覆盖路径。

也可在仓库根目录执行 `pip install -r requirements.txt`；依赖定义只维护在 `pyproject.toml`，
完整可重复环境以 `uv.lock` 为准。

## 登录与隐私

1. 点击右上角圆框内的粉色 **登录**（已有账号时点击头像），打开原生账号浮窗，再点击 **在 Chrome 中登录**。
   应用只启动自己拥有的临时浏览器会话，不读取已有 Chrome profile。
2. 在 Bilibili 官方页面完成登录。程序不填写密码、不处理验证码或 CAPTCHA。
   User-Agent 在打开登录页前从空白页读取，扫码后的跳转或换页不会中断这一读取。
3. 从独立浏览器会话读取 Bilibili 登录/设备 Cookie，由 bpi-py 验证账号身份。
   交接不再依赖原登录页保持打开，也不会在跳转中执行页面 JavaScript。
4. 登录完成后关闭临时 Chrome、清理其临时 profile，并回到下载器。后续 API 使用同一浏览器 UA。

这是实际 Chrome 登录，保留浏览器真实产生的设备 Cookie，不制造设备指纹，不模拟 Android 设备。
**Bilibili 最终显示的设备名称由平台决定，本应用不能保证它一定显示为 Chrome。**
浏览器自身加载官方网页的资源请求由该网页管理，不受下面的数据 API 请求节奏控制。
登录状态显示启动、扫码确认、身份验证与交接四个阶段；错误注明具体失败阶段，
不显示可能包含 Cookie、浏览器参数或签名 URL 的原始诊断。
取消或验证失败清除本次内存登录；身份验证不会自动重试。关闭临时窗口失败不会掩盖原始错误。

登录浮窗默认勾选 **记住登录**，用户可在本次登录前取消。采用便利优先的本机文件保存，
**不使用 macOS 钥匙串或其他系统凭据库**，恢复登录和打开缓存无需重复输入系统密码。
取消勾选只保留本次进程登录；已有的其他账号凭证不受影响。
使用保存的登录点击“使用已保存登录”；启动时不自动恢复或发账号请求。恢复时仍验证 provider 身份，
会话过期须重新在 Chrome 登录，不能通过本机缓存绕过平台认证。
“退出并忘记”清除当前账号的内存、保存凭证与缓存，不注销其他浏览器/手机客户端。
若登录有效但本机保存失败，会保留本次内存登录并明确提示保存失败，不显示无条件成功。

凭证按账号存放于 `private/accounts/<账号摘要>/session.json`，另有不含 Cookie 的当前账号指针。
目录权限 `0700`、凭证和数据库文件 `0600`（macOS/Linux）；凭证原子替换，避免保存中断损坏旧文件。
**Cookie 和缓存没有应用层加密**：这些权限能限制其他普通系统用户，但不能阻止同一系统用户下的程序、
管理员或拿到未加密磁盘的人读取。建议开启 FileVault、保护系统账号，不要共享本机数据目录或纳入公开备份。

高级 Cookie 输入仍然可用：按同一“记住登录”选项决定是否保存，不进入设置、终端参数、日志或下载 URL。
本版本不读取旧 `configuration/passport.json`、钥匙串条目或旧加密缓存，也不会自动转换、覆盖或删除它们。
升级后首次需重新登录一次；旧数据不作为新存储的兼容路径。
旧仓库历史中的凭证文件没有被改写历史；若其中曾保存仍有效的真实凭证，应在官方客户端撤销。

## 账号隔离的持久缓存

- macOS 数据位于 `~/Library/Application Support/Bilibili Downloader/private/<账号摘要>/cache.sqlite3`。
  每个账号一个普通 SQLite，记录校验账号和记录标识；正文、游标与图片在本机保存，不另生成或读取缓存密钥。
  登录凭证与内容缓存同属当前用户的 `private` 目录，权限和明文边界如上所述。
- 显式登录并经 provider 验证 UID 后，才打开该账号缓存；
  不能绕过登录直接浏览私信。切号只切换缓存，不删除其他账号；正常关闭保留缓存，
  “退出并忘记”停止任务、关闭缓存，再删除当前账号数据库和登录凭证。
  已关闭的缓存不能被晚到的读请求重新写回；同 UID 重新登录也隔离旧图片回调。
- “记住登录”只控制是否保存登录凭证；内容缓存仍按账号保留。
  本机目录不可用或缓存损坏时明确提示，本次仅用内存而不覆盖原缓存。
- 消息缓存最多 50 个会话，每个会话最近 500 条，记录总预算 16 MiB；会话列表最多缓存 100 项。
  消息及账号列表缓存有效期 30 天。正文与游标共同存在或共同淘汰，不能只留下更远游标；
  主动查看更多历史可在本次内存中超过 500 条，重启后从缓存最早条目继续按需往前读取。
- 图片按规范化 HTTPS URL 复用，不限制张数或磁盘总容量；每张原始响应上限 20 MiB。
  图片以原始二进制存入独立 SQLite BLOB 表，不做 Base64 编码；账号字段与 URL 摘要校验隔离。
  旧 Base64 图片在首次打开该账号缓存时原子转入 BLOB 并删除旧记录，不改变消息、游标或登录凭证。
  连续 30 天没有命中才过期：磁盘读取会续期，内存命中也沿用界面已有的合并定时器批量更新使用时间，
  只在原后台线程写本机数据库，不发 HTTP；旧账号回调不能续期新账号记录，正常关闭先提交待处理命中。
  打开缓存、写入图片或提交命中时清理过期图片，应用关闭时没有额外清理进程；大磁盘缓存仍需留意可用空间。
  内存解码缓存不限制张数，按上述 256 MiB 像素字节预算管理；正常重启不会清除有效磁盘图片。
  头像/封面命中缓存不消耗 HTTP 请求；新图片继续走既有白名单、无 Cookie 通路和请求间隔。
- 动态、关注和历史每类最多缓存 200 条已加载内容；恢复后明确标为缓存，分页游标与保存页面一致。
  不做后台历史补全、不根据恢复游标自动排空全部动态或观看历史。动态的前台新增检查仍为 60 秒，
  关注/历史只在显式刷新或加载更多时请求。
- 断线后的增量补齐有现有的 500 条单批安全上限；超过上限、身份异常、缓存写入失败或分页失败会停止，
  不推进到缺失数据之后。因此这是有界客户端缓存，不是无限期、无遗漏的消息归档。
  缓存不保存草稿、未确认发送意图或可重放写操作；重启绝不会自动重发私信。

## 请求节奏和失败处理

- 同一个应用实例的 API 和媒体请求共用一把串行锁；从上一请求**完整结束**到下一请求开始，
  随机等待 **0.5～1.5 秒**，启动后的第一个请求也等待。
- 借鉴 WhatsApp runtime 的 jitter / 防重试风暴原则，但不把其重连指数退避直接套在正常下载上。
- 不进行私信或账号状态的定时 HTTP 轮询，不在每个输入变动时自动请求。
  私信仅保留必要的 Broadcast 协议心跳；收藏夹和关注动态仅按上述前台、空闲、可见标签的规则检查变化。
  关注列表和观看历史没有定时轮询。
- HTTP 403/412/429、API `-352/-412` 会停止本实例后续请求；请到官方客户端检查账号，
  遵守平台要求后再重启。没有自动重试、换代理、换账号或伪造设备的逻辑。
- CDN 的正常 HTTPS 重定向逐跳验证域名，至多四次请求，也受随机间隔约束。
  不跟随任意网站、登录页或 HTTP 降级；媒体客户端不携带 Bilibili 登录 Cookie。
- 节奏控制**不能保证账号不被限制**。不要同时运行多个实例，也不要把批量下载当作不限量授权。

收藏夹扫描以实际分页结果而非数量统计决定是否继续。空页/重复页却仍宣称 `has_more`
会报错停止，不把不完整列表当作成功。没有 BVID 或非视频的收藏条目不会交给视频下载器。

媒体按固定大小流式写入独立临时目录，不把大视频载入内存；不需要先整段下载一遍探测长度。
完成转换后才原子发布最终文件。文件名包含 BV/CID，避免同名视频和不同分 P 冲突。
已有非空文件跳过，空文件、目录、链接会提示处理，**不覆盖用户已有文件**。
取消或失败会清理该任务的临时文件；已完成文件保留，重新运行会跳过它们。
FFmpeg 通过参数数组运行，不使用 `shell=True`。

## CLI

```sh
# 只检查元数据；不会下载媒体，默认预览最多 20 个分 P
uv run --frozen bili-download inspect BV178411i7AD
uv run --frozen bili-download inspect 'https://www.bilibili.com/video/BV178411i7AD?p=1'

# 输出到指定目录
uv run --frozen bili-download download BV178411i7AD --format mp4 --quality 16 --output ./downloads
uv run --frozen bili-download download BV178411i7AD --format mp3 --all-parts --output ./downloads
uv run --frozen bili-download download 123456 --mode favorite --format wav
uv run --frozen bili-download download 398421039 --mode user --pattern 'piano.*' --format mp3
uv run --frozen bili-download inspect ep746940

# 只有显式要求时才保存/读取本机登录
uv run --frozen bili-download login --remember
uv run --frozen bili-download download BV178411i7AD --use-saved-login
```

分 P 从 **1** 开始；`--all-parts` 优先于单个分 P。画质受账号和实际返回流约束，不保证请求到 1080P
就获得 1080P；视频流选择不会高于所选画质。输入必须是明确支持的 ID / bilibili.com 完整链接，
不自动展开 `b23.tv` 短链接或从任意粘贴文字中猜测目标。
